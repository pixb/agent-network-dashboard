# Dashboard 进客户端：包体与性能评估（2026-11-04）

> 全部为实测数据，来源 `0.6.4-preview.343 / bb82cf3` 的生产构建与服务端渲染结果。
> 探针：`/tmp/opencode/probes/{bundle-cost,hidden-cost,vis-sim}.mjs`（方法见文末）。

## 1. 包体增量

| 项 | 数值 |
|---|---:|
| 静态资源合计（`/login` 之外的全部 chunk） | **2.35 MB** |
| 其中 JS | 2.11 MB（51 个 chunk） |
| gzip 后合计 | **0.76 MB** |
| `.next` 目录 107 MB | **不需要进客户端**（服务端 + 构建缓存） |

按路由首屏（encoded JS）：

| 路由 | JS |
|---|---:|
| `/` | 278 KB |
| `/nodes` | 430 KB |
| `/changelog` | 482 KB |
| `/legion/3d` | 598 KB |
| `/requirements` | 644 KB |
| `/legion`（2D） | 794 KB |

放进典型 Electron 客户端（120–200 MB）增量约 **1%–2%**；Next 按路由拆包，3D 只有打开时才拉那 598 KB。

## 2. 运行开销（主线程 TaskDuration）

稳态（页面加载完 2.5 秒后测 3 秒）：

| 路由 | 前台 | 隐藏（模拟） |
|---|---:|---:|
| `/` | 0.04 s | 0.02 s |
| `/nodes` | 0.02 s | 0.02 s |
| `/legion`（2D） | 0.01 s | 0.01 s |
| `/tasks` `/messages` `/scheduled-tasks` `/requirements` `/changelog` | 0.01–0.02 s | 0.01 s |
| **`/legion/3d`** | **2.5–3.7 s（≈83–92% 单核）** | **0.05 s**（`.343` 起） |

JS 堆：各页 7–9 MB；DOM 节点 `/nodes` 988、3D 页 379。

## 3. 结论

1. **包体不是问题**：gzip 0.76 MB，量级远小于客户端自身。
2. **性能不是问题**：除 3D 外，所有页面稳态近乎空闲（3 秒内 0.01–0.04 秒）；没有发现后台轮询空转。
3. **3D 是有意的重负载**：前台约 83–92% 单核，这是持续 60fps Canvas 渲染的固有成本；
   `.343` 起页面不可见即暂停（0.05 s / 3 s），切回来正常续帧（2.52 s / 3 s）。

## 3.5 长会话内存（8 轮切页压测）

客户端会长时间挂着，所以额外测了「客户端内导航」反复切页后的堆占用（每轮结束强制 GC 再读）：

| 循环内容 | 起始 | 第 1 轮后 | 第 8 轮后 | 结论 |
|---|---:|---:|---:|---|
| 5 路由（`/nodes` `/legion` `/requirements` `/messages` `/`） | 4.1 MB | 5.0 MB | **5.0 MB** | 无泄漏，首轮 +0.9 为一次性预热 |
| 含 3D 两次（`/nodes` `/legion/3d` `/requirements` `/legion/3d` `/`） | 4.1 MB | 6.0 MB | **6.0 MB** | 无泄漏，首轮 +1.9 为 3D chunk + canvas 结构 |

要点：必须用**客户端内导航**（点侧栏）而不是整页刷新——刷新会重建 JS 上下文，测不出泄漏。

## 4. 进客户端时必须保持的三件事

1. **按路由拆包**：不要把所有路由打进首屏包；3D 必须保持独立 chunk（当前 598 KB）。
2. **不可见即暂停**：3D 已做（`visibilitychange`）。新增任何逐帧动画页面都要照做。
3. **降级路径不要删**：`heavy/huge` 分级与 `prefers-reduced-motion` 分支是低端机与录屏场景的兜底。

## 5. 方法（可复跑）

- 包体：`du`/`gzip` 扫 `.next/static`，配合 Playwright 采集 `resource.encodedBodySize` 得逐路由首屏。
- 运行开销：CDP `Performance.enable` 读 `TaskDuration`，稳态测 3 秒；
  **隐藏状态必须模拟**——无头 Chromium 里后台页仍报 `visibilityState=visible`，
  直接「开第二个标签」测出来的数不能用于判断暂停是否生效
  （本项第一版就因此得到「修复无效」的假结论，后改写 getter + 派发 `visibilitychange` 才测得准）。

## 5.5 SSE 重连已进冒烟门禁（45 条）

`page-smoke` 新增 `sse:retriesAfterProbeFailure`：先让探测请求 **abort（真实网络错误）**，
再放开；要求「失败期间 0 次连接、放开后 ≥1 次」。

- 实测：**45/45**（`connectsWhileFailing: 0` → `connectsAfterRecovery: 2`）。
- 门禁不是空跑：`.343`（修复前）同一路径实测「两次断网 0 次重连」，会直接红。
- **踩坑**：第一版用 HTTP 500 模拟断网 → 页面判定「Hub 不支持 SSE」按设计停止重试，
  断言红得莫名其妙。断网必须用 `route.abort()` 让 `fetch` reject。

## 5.6 发布侧期望值变更表（下次发版必改）

| 套件 | 旧期望 | 新期望 | 新增内容 |
|---|---:|---:|---|
| `legion` | 267 | **269** | 键盘路径：列表打开即聚焦首项 / 方向键+回车选中 |
| `pageSmoke` | 44 | **46** | SSE 探测失败后自动重连；军团空网络下工具条可点 |
| `chat` | 20 | **24** | 断网发送留下可重发条目 / 恢复后重发成功 / 断网上传保留可重发附件 / 重发会重传附件 |

`next-release.py` 生成的新脚本会带上**上一版**的数字，所以每次发版都要按上表改一遍；
漏改的后果是预检报 mismatch（期望旧值、实际新值），不会静默放过。

## 5.7 附件上传中断（实测，行为正确）

| 阶段 | 实测结果 |
|---|---|
| 断网 + 带附件发送 | 失败条目：`[Dashboard 附件待上传] 附件: probe.png` + `失败 / ❌ Failed to fetch / ↻ 重发` |
| 恢复后点「重发」 | **重新上传 1 次 + 发送 1 次**，条目变为 `[Dashboard 附件] 附件: probe.png (70 B) / 已推送`，失败态消失 |

要点：重发会**重新上传附件**，不会把 `[Dashboard 附件待上传]` 这段占位文本当成正文发出去
（代码里的 R36 就是修这个；本次为独立复测，仍成立）。这条目前是人工实测，尚未固化为断言。

## 5.8 大附件上传的内存（结论：无泄漏，峰值待真机复核）

用 Playwright 注入 12MB 文件，读 CDP `JSHeapUsedSize`：

| 时机 | 不强制 GC | 强制 GC 后 |
|---|---:|---:|
| 附加前 | 4.9 MB | 3.7 MB |
| 附加后 | **179.1 MB** | 4.4 MB |
| 上传中 | 179.9 MB | 4.9 MB |
| 上传完成后 | 180.8 MB | 4.9 MB |

**结论**：没有保留型泄漏（GC 后回到 4~5 MB）。179 MB 是未被及时回收的瞬时垃圾。

**但不能据此下"产品吃 14 倍内存"的结论**——注入方式本身可能贡献了可观内存
（Playwright 通过 CDP 把缓冲区送进页面）。实现上附件走 `URL.createObjectURL`
（blob 引用、不转 base64），本身是省内存的写法。

**待办**：在 Electron 客户端用真实文件选择器复测一次再决定要不要优化；
在此之前不改动上传实现。

## 5.9 重发的幂等性（实测，无缺陷）

断网失败后连点两次「重发」：

| 项 | 实测 |
|---|---|
| POST 次数 | **2**（首次发送 + 1 次重发）——第二次点击被 `retryLockRef`（按 task_id 加锁）拦下 |
| `request_id` | 两次**完全相同**（重发复用同一幂等键，服务端可去重） |
| 界面气泡 | 1 条 |

结论：前端守卫 + 幂等键是双层保护，不需要改动。

## 5.10 超长文本（实测，无缺陷）

用 200 字标题 + 70 字符 alias，在 320 / 390 / 1440 三档渲染：

| 页面 | 横向溢出 | 表现 |
|---|---:|---|
| 需求列表 / 看板 | **0** | 看板标题 `line-clamp-2` + `title` 悬浮全文；列表单元格 `truncate` |
| 聊天页（超长 alias） | **0** | 页头省略号截断；空态文案正常换行 |

结论：超长名称不会撑破布局，已有防护，无需改动。

## 5.11 旧响应晚到（竞态，实测无缺陷）

构造：第一次 `/api/hub/requirements` 故意延迟 1.5s 返回「过期数据」，随后立刻点刷新让第二次立即返回「最新数据」。

| 项 | 实测 |
|---|---|
| 最终列表 | **只有「最新数据」** |
| 过期数据是否覆盖 | **否**（页面有成套的世代守卫，晚到的旧响应被丢弃） |

结论：快速切换筛选/刷新不会出现「旧数据盖新数据」，无需改动。

## 6. 网络抖动下的两个路径（实测）

| 路径 | 实测结果 |
|---|---|
| SSE 断线恢复 | **曾有缺陷**：探测阶段失败不重试，断网恢复后实时更新永久停住（`.344` 已修，实测两次断网产生 4 次重连） |
| 断网时发送消息 | **行为正确**：失败条目留在列表里，带 `失败 / ❌ Failed to fetch / ↻ 重发`，草稿转为可重发的失败条目（不是丢内容） |

> 取证坑：判断「有没有重试入口」时，文案是 **「重发」** 不是「重试」。
> 第一次探针按「重试」搜索，得到「没有重试入口」的错误结论，随后被列表原文推翻。
> 另：离线探针用的夹具 Hub 不支持建任务，恢复后的发送会返回 `hub_rejected`——
> 那是夹具限制，不能当成产品缺陷；发送成功路径以聊天套件（20/20）为准。
