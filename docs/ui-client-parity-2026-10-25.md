### 数据源差异（这是根因）

- 客户端：`GET /api/networks/{networkId}/departments`
  → `{ departments: [{ id, name, parent_id, leader_user_id, sort, member_count, viewer_can? }], members: [{ user_id, department_id }] }`
  （`src/org-api.ts:63`，老 Hub 404 时整块不出现，回退行为必须保留）
- Dashboard：`GET /api/requirements/people/directory`（`app/api/hub/people/route.ts`）
  → 只有 `department: { id, name } | null`，**拿不到 parent_id、负责人、成员表**。

**所以「军团图」原先画的是扁平部门，不是军团真实编制。**

→ 2026-10-25 晚已修：新增 `/api/hub/departments` 代理（状态码原样透传，404 表示
「这版 Hub 没有这条路由」），`legion-layout` 改为按树递归，半径随深度从 0.30 递增到

## 七、三态普查（2026-10-26，`28f54c5`）

写报告前先查了「读失败时页面说什么」。结论不是「某些页面缺 loading」，
而是**一个共享 SWR key 的吞错污染了全站**：

`/api/hub/status` 同时被 `useSessions()`（页面）和 `Sidebar` 注册。
Sidebar 的 `statusFetcher` 在非 2xx 时返回 `{ sessions: [] }`；SWR 按 key
去重，Sidebar 先解析出的「空」写进全局缓存，于是所有页面拿到的都是**空数组
而不是 error**，空态文案就把「Hub 读不到」说成「本来就没有」：

| 页面 | 读失败时的旧文案 | 实际含义 |
| --- | --- | --- |
| `/nodes` | 「Run this in a fresh terminal to register an agent…」 | 不是新装，是没读到 |
| `/versions` | 「在线 0 / 落后 0」（且画成统计卡） | 不是全对齐，是没读到 |
| `/tasks` | 「Tasks will appear here when agents send them」 | 不是没任务，是没读到 |
| `/messages` | 空态（`useMessages` 连 error 都没解构） | 不是没消息，是没读到 |

修法分三层（都在同一个提交里）：

1. **吞错源头**：`Sidebar.statusFetcher` 非 2xx 抛错（401 仍跳登录）；
   `useSessions` 的共享 `fetcher` 对 `!res.ok` 抛错。
2. **代理层状态码**：`/api/hub/status`、`/api/hub/messages` 上游非 2xx 不再
   包成 200；`/api/hub/tasks` 的 `/api/completions` 回退也失败时返回 502，
   而不是 `{ ok: true, tasks: [] }`。
3. **页面三态互斥**：四页只在「真·空且没报错」时渲染空态；读失败给错误卡 +
   重试；已有陈旧数据时给一条「下面是上一次读到的」。`/versions` 读失败时
   不画 0/0 统计。

验收用 stub Hub 独立制造 500：四页均出现错误卡、无空态引导；切回 200 后四页
正常且无错误文案。契约写在 `app/lib/hub-error-propagation.test.mjs`（4 条），
因为这类问题发生在 SWR 缓存去重之前，e2e 很难稳定复现。

**第二轮收口（2026-10-26，`ec6e9c8`）**：把「页面当权威数据用」的代理逐条修了。

| 代理 | 旧行为 | 现在 |
| --- | --- | --- |
| `/api/hub/tokens` | 失败 → 200 `{tokens: []}` | 非 2xx 透传（404→502）；设置页命中已有的错误卡 |
| `/api/hub/networks` | 失败 → 200 `{networks: []}` | 404 标 `unavailable`，其余透传；Sidebar `networkFetcher` 不再吞错（同一个 SWR key 污染模式） |
| `/api/hub/task-events` | 失败 → 200 `{events: []}` | 404 标 `unavailable`（老 Hub 无端点），其余透传 |
| `/api/hub/nodes` | 失败 → 200 `{nodes: []}` | 先走 `/api/status` 兜底（老 Hub 无 `/api/nodes` 是设计好的降级），两个上游都挂才 502；兜底映射合并成 `nodesFromSessions()` |

设置页 `/settings/networks` 补了 error / unavailable / loading 三态互斥——
它的注释早就写着「空列表和读失败无法区分」，但代码里没解构 `error`。

**仍未覆盖**：`/api/hub/audit-log` 等少数路由仍有 graceful fallback，其页面
不把结果当权威数据（只做附加信息展示），暂不动。

## 十一、军团 3D 网络拓扑（2026-10-26，`0b58b5e`）

owner 要求「3D 版本网络拓扑，给看到军团的人大大的震撼」。与神明分工：她定
视觉参数、我实现渲染与门禁。

### 为什么不引 three.js
一个页面不值得把 WebGL 运行时塞进离线部署包（包体、CSP、e2e 截图都会受牵连）。
3D 的部分其实是**投影数学**，用 Canvas 2D + 透视除法就够：节点数量在几十个
量级，性能不是瓶颈，控制力反而更强（每个像素都能按 token 上色）。

### 结构与约束

| 层 | 文件 | 职责 |
| --- | --- | --- |
| 数学 | `app/lib/legion-3d.ts` | 极坐标→3D、旋转、投影、深度排序、命中、雾化、轨道采样（10 条单测） |
| 取数 | `app/lib/legion-data.ts` | 2D/3D 共用：404=能力缺失、其余非 2xx 抛、401 交登录 |
| 渲染 | `app/legion/3d/page.tsx` | Canvas 绘制、交互、详情卡、导出、三态 |

三条和 2D 页一致的硬约束：
1. 坐标只来自纯函数，组件里不许出现画节点的 `Math.sin/cos`（有源码契约测试）；
2. 颜色只读 token，JSX 里不出现 `#rrggbb`；
3. 空 / 加载 / 401 / 500 各有独立状态，空态只在数据到位且确实只有圆心时出现。

### 视觉元素
星野 + 径向辉光、部门扇区弧带（一眼看出「这块是哪个部门」）、地面网格
（给纵深参照）、核心呼吸（6% 幅度）、连线流动光点、每层环上两颗卫星、
深度雾化与径向标签（避免正下方标签糊成一团）。

### 交互与出口
拖动环绕、滚轮/双指缩放、点节点看详情（含部门路径与 Agent 深链）、
方向键旋转 / `R` 重置 / `Esc` 取消选中、自转在 2.6s 无操作后恢复；
导出当前视角 PNG；与 `/legion` 双向互达。

### 神明两段脚本的吸收（`2925491`）

神明把她 PPT 的 cover14（深色）/ phalanx18（浅色）脚本发了过来。能搬的
「材质」全部搬到 Canvas 2D：

| 她的做法 | 我们的落地 |
| --- | --- |
| 连线 = 二次曲线，控制点法向偏移 18% | 控制点法向偏移 16%、双向交替，避免所有线朝同一边鼓 |
| 三层：宽光晕 + 实线 + 白色 dash 2/22 | 宽光晕 9px@.34（blur 3）→ 实线 2px@.85 → dash 2/22 + lineDashOffset 动画 |
| 双向彗星：亮头（白芯+彩描边）+ 6 段尾巴 | 每条边两个数据包，沿二次贝塞尔求值跑 |

| 团队内弧：细彩线 + 白色短划 1.5/11 | 部门内相邻成员之间同款细弧，比部门间连线细一档 |
| 投影 P() = 1/(1+Z·0.11) | 固定 dist=6（≈1/6 柔化），缩放与透视拆开 |

没搬的：`roundPath()` 圆角平台是 2.5D 方阵列队，我们的 3D 轨道投影里没有
平台这个对应物，硬搬会多出一层没有语义的装饰。

### 3D 性能与导出（`19043fb`）

**压测**：造了 BIG 数据集（8 部门 / 60 人 / 90 Agent = 158 节点）跑帧间隔。
初版中位 33.3ms（30fps）、p95 50ms。逐段计时后发现 JS 只占 ~1.8ms ——
瓶颈在光栅化：逐节点 `shadowBlur` + 逐边模糊在软件光栅（headless / 无 GPU
的窄带云主机）下极贵。

**两处结构性改法**：
| 改法 | 收益 |
| --- | --- |
| 节点光晕 → 预渲染 128×128 径向渐变精灵（按色缓存，`drawImage` 缩放） | 去掉逐帧 `shadowBlur` |
| 背景（底色 + 染色渐变 + 星野）→ 离屏 canvas，每帧只 `drawImage` | 少两次全画布渐变填充 |
| 连线光晕 → 两遍加宽描边（10px@.07 + 5px@.10） | 去掉整层模糊 |

叠加规模降级（>80 节点：连线光晕仅高亮边、数据包每 6 条边、白色短划每 3 条边、
小节点不画外晕、标签只留核心/部门/高亮）：**33.3ms → 16.7ms（60fps）**，
p95 50 → 33.4ms，视觉元素一个没少；小网络视觉不变。

**导出**补齐：此前只导裸画布，现在带标题「军团 · 3D 网络拓扑」、部门/成员/
Agent 计数、导出时间、底部状态图例、`ANet · Legion 3D` 水印（1072×959）。

### 柔化（`d170858`）

亮青换成更柔的蓝。3D 页同步收一档：连线光晕 10px@.07 → 6px@.04、实线
2px@.85 → 1.6px@.62、白色短划 alpha .75 → .48、数据包尾巴 .42 → .30、
环上彗星 .62 → .45。

深底亮样本 2127 → 1903（变暗符合预期），浅底不变。要点：柔化只动「装饰层」，
节点白芯 + 彩色描边的对比度保持原样 —— 亮线可以淡，节点不能糊。

### 标签避让与搜索（`2b2e2ba`、`d099542`）

## 十二、按部门筛任务（2026-10-26，`153e685`）

客户端能「点部门看这个部门的任务」，Hub 的任务接口只有 `status` /
`from_name` / `to_name` —— 没有 `department_id`。这轮先做不依赖新合同的投影版：

| 层 | 实现 |
| --- | --- |
| 纯函数 `app/lib/dept-task-filter.ts` | alias→人→部门反查、部门子树展开、任务过滤、下拉选项 |
| `/tasks` 过滤行 | 新增「Dept」下拉（缩进表示层级）；状态计数/分布条/列表都基于筛选后的集合 |
| 口径说明 | 「命中数为当前这 N 条任务里的投影结果，不是部门全量」 |
| 空态 | 筛不到时写「这个部门在当前这批任务里没有记录」，不写「该部门没有任务」 |

诚实边界（都写进单测）：
- `members` 落位表是权威，`null` 表示「明确未分配」，**不回退**到
  `person.department` 的旧值；
- 不认识的 alias（离职 / 不在通讯录）一律不算任何部门，宁可显示未归属；
- 筛父部门要带上子部门；
- 兼容路径只给 `from_alias`/`to_alias` 时也能筛出来；
- 通讯录/部门树读不到 → 只是没有下拉框，任务列表照常。

等通信欧确认 Hub 的真实合同（`department_id` 服务端过滤或部门群接口）后，
再把投影换成服务端口径。

### 未归属分组与大网络提示（`7951bfd`、`06d1b6f`）

- **未归属**：部门筛选上线后暴露一个洞 —— 参与者不在通讯录（外部 Agent、
  离职的人）或没分配部门时，这些任务在任何部门筛选下都不出现。现在 Dept
  下拉多一项「未归属（N）」；判定规则是**所有**参与者都落不到部门才算，
  只要有一个能落到部门就不算；字段全空时不算未归属（没信息 ≠ 未分配）。
- **3D 规模提示**：节点 >120 时在底部给一条可关掉的提示（带真实节点数），
  关闭后写 `sessionStorage`，本次会话不再弹。

### 部门任务深链与 3D 聚焦朝向（`faec29e`）

- `/org` 每个部门行加「N 条任务 →」徽标，点进去是 `/tasks?department=<id>`，
  落地即按该部门筛选。计数复用 `dept-task-filter` 的投影口径，只取一页
  任务，所以数字是「当前这批任务里的命中数」—— 写在 title 里，不冒充全量。
  老 Hub 没有部门树时 group id 是合成的，按部门名再兜一层。
- 3D 部门聚焦时镜头转到该扇区：yaw 目标取节点 angle、最短路径缓动，
  用户拖动/按键立即放弃自动对准，取消聚焦也清目标。聚焦不再只是淡化别人。

### 部门筛选可分享 + 3D 聚焦更彻底（`61dd482`、`4bfa508`）

- `/tasks` 的部门筛选写回 URL（`replaceState`，保留其它参数）：刷新不丢、
  可把「某部门的这批任务」直接发给同事；history 被禁用时只是不写 URL。

  其余扇区 .04→.015 / .08→.03 —— 之前只淡节点，别人的部门扇区还亮着，
  「只留这一个部门」的感觉不彻底。

### 3D 触屏与键盘（`8bc279b`）

- 触屏实测（375×812、hasTouch + CDP 真双指触摸事件）：双指张开后亮像素

### 2D/3D 键盘对齐与 `/` 的归属（`098c063`）

2D 页原来有三个键盘问题：搜索框里打空格会触发「折叠选中部门」并 preventDefault；

### 组合态：搜索与部门聚焦互斥（`61a7e76`）

### 高亮态预算（`75bc7a9`）

408 节点 + 搜索命中全部部门（极端高亮态）时，逐条边画光晕 + 逐个标签

（>80 节点 96 条）、标签最多 16 个（>80 节点 40 个），agent 在大网络里
不再强制出标签。

408 节点稳态实测：idle / 搜索 / 窄搜索 / 清空 四种状态都是中位 16.7ms
（60fps）；聚焦态下高亮部门清晰、其余扇区明显压暗。

### 3D 自动取景（2026-10-27）

默认 `zoom=1.12` 时整张图只占画布 40% 左右，四周大半是空的 —— 1080p 投影到

实测（stub）：3 人网络 112% → **193%**；408 节点网络 **144%**，整张拓扑完整落在画面内，

### 3D 取景补两处（2026-10-27）

## 36. 2026-11-03 续十七：套件全绿 ≠ 证据可用

`.308` 发布被拦了三次，每次拦下来的都不是产品缺陷，而是**证据本身不可信**。这三条现在都有会失败的断言守着。

### 36.2 同一 SHA 不够，还要同一份构建

- `sourceCommit` 与发布 SHA 不一致——我用了功能分支的工作区跑套件；

| 检查 | 含义 |
|---|---|

## 35. 2026-11-03 续十六：隐藏控件之前，先问它是不是唯一入口

### 35.1 一次自摆事故（`.297` → `.307`）
为了给手机首屏省 30px，`.297` 把 `Refresh` 在窄屏隐藏了。结果列表只剩“导航/改筛选时自动刷新”，
用户**没有任何主动刷新入口**——功能被顺手删掉了，而且套件当时没有判据能发现。

`.307` 在「筛选」旁补了紧凑的「刷新」按钮（44px），并加两条判据：
- `narrow:listRefreshReachable`：可见且高度达标；
- `narrow:listRefreshRefetches`：点击后**拦截到的请求数增加**（764 → 767）。

第二条是关键：只看按钮存在，很容易做出“点了不请求”的装饰品。

规则：**隐藏一个控件之前，先确认它是某件事的唯一路径**；若是，必须先给它安排替代入口。
本轮按此复核了其余为省空间的隐藏项：副标题（任务入口在底栏仍有）、归档提示（仅空闲态隐藏，
错误/登录/搜索中保留）、已逾期与优先级行（进筛选面板）、军团说明行（纯解释，无路径）。

### 35.2 手机 3D 工具条：单行不等于能用
两行工具条占约 90px，收成一行省下 50px。但单行化本身引出三个问题，全部由截图或断言抓到：

| 现象 | 根因 | 处理 |
|---|---|---|
| 按钮标签折成两行（“自转/静止”） | `flex-nowrap` 不阻止 flex 子项收缩 | `[&>*]:shrink-0` |
| 「更多操作」被挤出屏幕 | 排序靠后 | 四个次要开关 `max-sm:order-last` |
| 排序类加错元素（落在舞台根节点上） | 补丁匹配错位置 | 精确定位目标类名 |

判据用**工具条高度**（≤56px）判断单行，而不是数不同 `top` 的个数——「光流」按钮是 44px 高，
`top` 与邻居天然不同，数 `top` 会把单行误判成两行。

### 35.3 重置必须回到“默认”，不是“100%”
窄屏自动取景把 `k` 提到约 1.36，而「重置」硬设 `k = 1`：按完重置，图比刚打开时更小。
改为清标记 + 重新取景；实测 `k` 1.3563 → 1.6276（放大）→ **1.3563**（重置），与取景值一致。

## 34. 2026-11-03 续十五：把图「放大」这件事，两个视图都已到头

同日试了两条不同的路，结论都是**不改**，但理由完全不同，值得分开记。

### 34.1 2D 桌面：放大后一定被浮层挡住（试过五轮，回退）
1440 下 2D 节点并集只占舞台宽 **52.7%**（468/888），看着确实浪费。于是让取景按宽度放大，
结果依次撞上：标题栏 → 舞台内统计条/缩放控件 → 打开的节点列表 → 换一个节点再撞。
每次修正都只是把「被挡的是谁」换了个人。

原因：桌面舞台是「宽而矮」（62vh），而图是圆的；一旦接近可用高度上限，剩下的宽度就用来
把节点推到浮层底下。**这不是取景参数问题，是舞台形状与浮层位置的约束**。
处理：回退，并把 0.527 作为基线写进套件注释（「基线，不是目标」）。

### 34.2 3D 桌面：已经在可用区域的上限（无需改）
1440 下 3D 实体包围盒 514×489，占画布 41.7% 宽、56.3% 高，看起来也偏小。
但取景目标本来就是「较短边可用区域的 90%」：顶部扣掉标题与工具条约 265px、底部 72px 后，
可用高度约 530px，目标尺寸约 **477px**，实测 **489px** —— 说明已经贴在上限。

所以 41.7% 的「宽度占比」是被顶部扣掉的结果，不是取景偷懒。要更大只能继续压顶部，
而桌面顶部已经只剩一行工具条。

### 34.3 手机端同理
390 下 3D 占宽 71%（宽度受限），继续压缩头部只会让图**居中**，不会变大。
`.303`/`.304` 压缩头部（说明行、工具条）解决的是「首屏进入更早」，不是「图更大」。

一句话：**先判断约束是宽度、高度还是浮层**，再决定要不要调取景；三者的处理方式完全不同。

## 33. 2026-11-03 续十四：判据要能区分「做对了」和「碰巧没坏」

今天有两条断言先写错了，都是同一个毛病：**不管修没修都会绿**。

### 33.1 手机 2D 的面板可见性
现象：点完部门，详情面板在画布下方，只露出贴着底部的几行，看起来像“点了没反应”。

第一版断言写成「面板 `top < 视口高`」——不修也能过（实测约 740/900）。
改成 `bottom <= 视口高 − 56`（避开手机 Tab 栏）后，才有区分力；
同时产品侧的 `scrollIntoView({ block: 'nearest' })` 会让面板底边正好贴住视口底部、
被 Tab 栏压住，也一并改成居中。实测 `top 469 / bottom 796`（上限 844）。

### 33.2 用例之间的污染
新增的「3D 拖转后从列表选中」用例改了视角，而 3D 会把视角写进 `localStorage`；
下一条用例 `?focus=平台` 的期望缩放（≥130%）只拿到 87%，红在**别处**。
失败点看起来在后一个用例，根因却在前一个用例没有收尾。

处理：该用例结束时清掉 `legion3d-*` 键，恢复后续前置条件。
写新用例的固定要求：**自己改过的共享状态（视角、选中、筛选、localStorage）必须自己还原**。

### 33.3 判据设计清单
1. 先问「不改代码它会不会也通过」——会，就说明判据太松；
2. 断言读**结果**（位置、变换、像素、DOM 几何），不读「函数被调用过」；
3. 涉及手机时，判据要包含**底部 Tab 栏高度**，否则“擦边可见”会冒充“可用”；
4. 新用例必须能独立运行，且不改变后续用例的前提。

## 32. 2026-11-03 续十三：手机上「控件合格 ≠ 手指能用」

### 32.1 台账：两个视图的手势能力曾经不对等
3D 军团早已支持单指旋转 + 双指缩放；2D 只有滚轮、`+/-` 按钮和键盘，**双指没有反应**。
同一个产品里两套手势语汇，用户在手机上只会认为 2D 坏了。

`.300` 补齐 2D：单指平移（原有）、双指按 `span/prevSpan` 缩放、以两指中点为锚（与滚轮同规则），
走同一个 `zoomBy`，所以手动操作同样会停止窄屏自动取景；补 `onPointerCancel` 避免中断手势残留指针。

### 32.2 怎么验的：读变换，不信“事件似乎触发了”
Playwright 的 `touchscreen` 只有 tap，多指必须用 CDP `Input.dispatchTouchEvent`。
断言直接读结果，而不是读“处理函数被调用过”：

| 断言 | 实测 |
|---|---|
| `390:3dTouchDragRotates` | `data-view-yaw` 0.62 → 1.58 |
| `390:3dTouchPinchZooms` | `data-zoom` 79% → 306% |
| `390:2dTouchDragPans` | `<g>` `translate.x` −63.8 → 16.2 |
| `390:2dTouchPinchZooms` | `<g>` `scale(k)` 1.356 → 2.863 |

注：3D 双指 3.88 倍指距对应 3.87 倍缩放，是**成正比**的（地图类手势的标准行为），
不是“太灵敏”的缺陷。若日后要手感更柔和，应加阻尼曲线，而不是改断言。

## 31. 2026-11-03 续十二：把「叠印」变成可自动发现的问题

`.298` 的「重命名 / 归档」叠在一起，是靠看截图撞见的。人眼看几十个控件必然漏，

### 31.1 规则
同一页面内任意两个可见的 `button` / `a[href]`，若相交面积超过较小者的一半，就记录

## 30. 2026-11-02 续十一：窄屏取景——2D 该放大，3D 不该

两个视图都是“图偏小”，但结论相反，区别在于取景的**约束**不同。

### 30.1 2D：按节点并集取景（`.296`）
基线：390px 下节点并集只占舞台宽度 **64.9%**（232/358），竖直 40.3%，字被一起缩小。

改法：窄屏按并集把 `k` 提到“用满 88% 宽度”（上限 1.8），桌面保持 1；
用户自己缩放过就不再自动干预，「重置」清标记重算。

踩坑：变焦绕原点，需要补 `tx/ty`。第一版按**舞台中心**补偿，而图形质心本身偏上，
放大把偏移一起放大，成员头像顶到统计条（截图发现）。正确做法是解出**图形自身包围盒中心**
并对位到舞台中心，再留 64px 顶部避让。

实测：占宽 64.9% → **88.0%**，占高 40.3% → 54.6%，不越界；断言 `390:2dFillsWidth` / `390:2dStaysInsideStage`。

### 30.2 3D：维持现状（有数据支撑的“不改”）
390px 下 3D 实体包围盒占宽 **71%**（276/390），看起来还能放大，但它的取景约束更多：

- 自动取景把**环路径与实体**一起纳入（`fitProjectedBodies`），不只是节点；
- 安全区扣掉了顶部工具栏与底部控制条；
- 透视投影下越靠外的环被压缩得更扁，继续放大首先裁掉的就是环。

所以 71% 是“把结构装全”的结果，不是漏跑的取景。强行拉到 88% 会先丢环。
基线记录在案，日后若要做“手机上也放大”的版本，需要先决定**接受裁掉外环**，而不是调一个系数。

## 29. 2026-11-02 续十：低透明度下的文字，与一个被误判为“偶发”的竞态

### 29.1 文字要么清楚，要么不画
两处都是同一类问题，先后被截图抓到：

|---|---|---|
| 3D 生产密度 | 子部门淡到 `alpha 0.12` 仍在画字，出现“看得出形状、读不出内容”的部门名 | `alpha < 0.5` 不画节点文字 |
| 2D 聚焦某部门 | 其它节点降到 `opacity 0.18`，标签照画，糊成灰雾 | `[data-dim='true'] text { display:none }`，只留轮廓 |

判据都落在“实际绘制了什么”上，而不是开关状态：
3D 每帧写 `data-node-text-alpha`（实测 0.77）；2D 用 DOM 计算样式统计调暗组里的可见文字（0 个）。
两侧都配了反向断言，防止“一刀切全隐藏”也算通过。

### 29.2 演示态 Esc 丢键：不是偶发，是覆盖
`?present=1` 深链进入后立刻按 Esc，偶尔无效。`.293` 曾把原因判为“监听器挂得太晚”，
改成常驻后症状变轻但没消失——说明判断不完整。

真正的顺序是：

1. 深链那一次 render 里 `presenting` 还是 `false`；
2. 深链 effect 把 `presentingRef.current = true`，并排队 setState；
3. **同一次提交**里，`useEffect(() => { presentingRef.current = presenting })` 用旧的 `false` 覆盖回去；
4. 下一次 render 才恢复。按键落在这一个窗口内就被忽略。

处理：删掉“跟随 state”的 ref effect，`presentingRef` 只在真正改变演示状态的四处显式写
（深链 / 切换 / 退出 / 开始录屏）；Esc 监听移到捕获阶段，别的组件 `stopPropagation` 也拦不住。

教训：**用 ref 做同步判断时，不要再挂一个“跟随 state”的 effect**——两者在同一提交里会互相打架。
另外，单次通过不足以证明竞态消失：断言改成“深链进入 → Esc 连做 3 次必须全中”。

## 28. 2026-11-02 续九：军团 3D 的实测基线（先量再改）

视觉问题只靠截图判断，很容易改错方向。三组数字现在由画布自己写出，套件读它们：

| 指标 | 位置 | 生产密度实测 |
|---|---|---|
| `data-fit-bounds` / `data-fit-view` | 所有节点实体（含描边）的屏幕包围盒 | 390px：`64,297 → 340,560`（画布 390×763），**未越界** |
| `data-node-text-alpha` | 本帧节点文字用过的最低透明度 | **0.77**（门槛 0.5） |
| `data-noise` | `agents=…,offline=…,cover=…` | `agents=42, offline=42, cover=0.026` |

结论与处理：

- **窄屏没有被裁**。上一轮怀疑来自一张“聚焦之后”的截图——聚焦本就会推近裁掉其它部门，那是设计行为。
  新增 `390:3dGraphFitsCanvas` 守住这一点（旧断言只说“页面不横向滚动”，那与图有没有被裁无关）。
- **幽灵标签是真的**：子部门淡到 0.12 时仍在画字。改为 `alpha < 0.5` 不画文字，`dense:3dNoGhostLabels` 守门。
- **42 个未上报 Agent 不构成噪声**：实体面积只占画布 2.6%，结构（环、部门、连线）清晰可读。
  因此**不做**按部门聚合；聚合会牺牲“哪个 Agent 在哪”的信息，代价大于收益。这条基线留作日后再评估的对照。

## 27. 2026-11-02 续八：演示 / 录屏链路（一条链接跑完）

|---|---|

## 25. 2026-11-02 续六：批量操作的健壮性（全部有断言）

| 行为 | 断言 | 实测 |
|---|---|---|
| 请求飞行中，批量「应用」按钮 | `bulk:applyDisabledWhileBusy` | disabled |
| 请求次数 | `bulk:noDuplicateRequests` | 每项 1 次，无重复 |
| 部分失败 | `bulk:partialFailureKeepsFailedSelected` | 只留失败项选中 |
| 失败原因 | `bulk:groupsSameReason` | 按原因归并计数 |
| 重试 | `bulk:retrySendsOnlyFailedItem` | 只补发失败项（+1 次） |

夹具为此新增 `slow_patch`（PATCH 延迟 500ms）与 `deny_ids`（多项同时拒绝）。

两条经验：断言“结束后按钮可用”是错的——成功路径会清空选中，按钮因**无选中**而禁用；
新增用例若改变选中集合，结束时要还原，否则后面的用例（如「清空选择」）会因为 disabled 而卡住。

### 20.3 发布链路的两次自身失误（已固化为步骤）

- 发布验收进行中修改共享探针，会把“探针变严”误记为产品回归；`.259` 首轮即因此被判失败
