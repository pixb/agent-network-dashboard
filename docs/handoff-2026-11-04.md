## 5.5 新增工具：套件期望值自检（`deploy/check-suite-expectations.py`）

今天两次因为「套件增删了断言、生成器仍抄上一版数字」而在 35 分钟验收后才被预检拦下。
这个工具把发现提前到生成流水线的那一刻。

```bash
# 生成完 publish-<N>.py 之后，拿它对「上一版实测」核一遍（最早发现漂移）
python3 deploy/check-suite-expectations.py --label 346 --against 345

# 验收跑完后核对本版实测
python3 deploy/check-suite-expectations.py --label 346

# 自动改写脚本里的数字（改完会再核一遍，真对齐才返回 0）
python3 deploy/check-suite-expectations.py --label 346 --fix
```

`next-release.py` 生成脚本后会自动跑 `--against <上一版>`；不一致时打印
「套件期望值可能与上一版实测不一致」并列出具体套件。

**已验证**：故意把 `chat 22` 改回 `20`、`legion 269` 改回 `260`，工具报两条 MISMATCH；
`--fix` 能逐条改回并复验通过（exit 0）。

> 注意：该脚本与其它 `deploy/` 工具一样位于工作区（不在 git 仓库）——
> 需要版本管理时请复制到仓库 `scripts/` 并登记 OSS 白名单。

## 5.6 两个操作护栏（今天亲手犯错换来的）

### 5.6.1 标签守卫（82 个 `deploy/run-*.py`）

手动回归不得再用 `<suite>-<版本号>` 这种名字——它会让验收脚本把旧输出当成新结果、
或拒绝启动（今天两次）。现在这类标签会被直接拒绝，提示改用 `-manual`：

```
$ python3 deploy/run-page-smoke.py --label smoke-347 ...
label 'smoke-347' 看起来是发布流水线的标签（<suite>-<版本号>）；手动回归请加 -manual 后缀
(exit 1)
```

发布流水线自身放行：`run-<label>-final-acceptance.py` 顶部设置了
`ANET_ALLOW_RELEASE_LABEL=1`，只有显式带这个环境变量才会放行。

### 5.6.3 脚本路径预检（`deploy/preflight-script-paths.py`）

验收脚本里引用的每个 `deploy/*.py` 都必须真实存在、且带 `--source` 参数。今天我把
`run-chat-attribution-acceptance.py` 写成了 `run-chat-acceptance.py`，命令"启动"了、
几秒后才失败，白等一轮。现在：

$ python3 deploy/preflight-script-paths.py --script /tmp/mut.py   # 故意写错名字

paths: 🔴 fix these before starting a run (a typo here costs a full cycle)

`next-release.py` 生成验收脚本后会立刻跑一次，不通过直接 `SystemExit`。

### 5.6.2 生成器的分支守卫（`next-release.py`）

生成流水线前检查主仓：分支必须是 `main`、工作树必须干净，否则直接退出。
起因是今天有一次提交落在错误分支，推送后远端没变而生成器仍在继续。

> 两条护栏都属于 `deploy/` 工作区脚本（不在 git 仓库）。
> 新增发布流程脚本时记得沿用同样的守卫，或把它们迁进仓库 `scripts/` 并登记白名单。

## 5.7 发布重启的端口竞态（已从生成器修正）

查 `~/.pm2/logs/anet-dashboard-error.log` 发现 **34,392 条**
`listen EADDRINUSE: address already in use 127.0.0.1:3001`。

原因：发布脚本是 `pm2 delete` 紧接着 `pm2 start`，而 `pm2 delete` 返回时旧 next-server
往往还没释放端口。前几次发布靠 pm2 重试收敛了，但每次都在赌。

`next-release.py` 现在会给生成的 `publish-<label>.py` 注入「等端口释放」：

```python
pm2('delete', NAME)
_deadline = time.monotonic() + 20
while time.monotonic() < _deadline:
    with socket.socket() as _sock:
        if _sock.connect_ex(('127.0.0.1', 3001)) != 0:
            break
    time.sleep(0.25)
pm2('start', str(config), '--only', NAME)
```

**尚未在真实发布中验证**：下一次发布请对比「错误日志里 EADDRINUSE 是否还新增」。

另注：日志里还有一条安全提示 `using CommHub token as login password. Set DASHBOARD_PASSWORD`——
生产目前用 Hub token 当登录口令。这属于运维决策，我没有改动，需要管理员确认是否要独立口令。

## 5.8 孤儿服务清理（`deploy/cleanup-orphans.py`）

巡检时发现开发树里挂着 3 个 Next 服务，已跑 1–2.8 天，共约 **974 MB**（其中一个 728 MB 占着 3000 端口），
都是探针超时中断后没回收的。

工具规则（安全优先）：

- 只匹配 cmdline 含 `next-server` / `next start` 的进程；
- 只处理 cwd 在开发树 `agent-network-dashboard` 内的；`releases/` 与其它工作区一律不动；
- 监听 3001 的进程永不处理；
- **默认 dry-run**，清理需 `--yes`。

```
$ python3 deploy/cleanup-orphans.py
orphans: 1 development-tree Next server(s), ~11 MB RSS
  pid 1079537  11 MB  0.0 h  ports [3999]  /home/vansin/comm-dash-ou/agent-network-dashboard
orphans: dry-run — re-run with --yes to kill
```

已验证：造一个 cwd 在开发树、监听 3999 的假孤儿 → 能被识别并只杀它；
执行后复查为空，生产 `0.6.4-preview.346`（3001）健康不受影响。

> 探针跑挂时建议先跑一次本工具。历史上这类残留会静默吃掉上 GB 内存。
