## 二、性能：真正的根因不是"串行"

最初的判断是「请求太多被串行」，实测推翻：

- 单请求 TTFB 只有 82–275 ms（DNS 1–68ms、TCP 2–8ms、TLS 70–264ms）
- 但 `/api/hub/status` 响应体 **709,690 B**，且**未压缩**（`Accept-Encoding: identity` 与 `gzip` 下载字节数完全相同）
- 公网带宽约 240 KB/s → 单这一份 ≈3 秒；加 tasks 296KB、messages 315KB ≈6 秒，与首屏 6.7 秒吻合

**结论：先量「每个请求传了多少字节」，再谈请求数/缓存。**

## 三、测量方法（血的教训）

| 坑 | 表现 | 正确做法 |
|---|---|---|
| 跨环境对比 | 本机 0.6s vs 公网 6.7s，误以为应用慢 | 同机同 Hub 对照，或用 CDP 限速到公网带宽 |
| 统计过早 | 数字出现即读 `transferSize`，大请求记成 0（首页 774KB 假象） | 沉降 8 秒后再统计 |
| DOM 指标被骨架污染 | 「军团页出现图例」3001/3002 都 550ms | 用请求级指标（duration + transferSize） |
| 共享机器负载 | 帧率断言 `median<26ms` 在 load 11 时红（实测常数 22.7ms） | 高负载重采样并记录 `load1`；不放宽阈值 |
| 时间窗断言 | `tour:yawSettlesWithin500ms` 在 load 11.6 红（缓动 480ms，余量 20ms） | 同上：重采样，阈值不变 |

## 四、验收基建的 5 类「会骗人」缺陷（均已修）

1. **日期炸弹**：`verify-detail.mjs` 断言「还原截止日期后不再是 overdue」，夹具 `due=2026-11-05`，越过该日期后结构上永不成立 → 改为「回到原 kind」
2. **半截结果复用**：`run-<N>-final-acceptance.py` 只比 `passed==total`，探针崩溃留下的 9/9 会被当成 115 项全过 → 增加 `exits.exit == 0` 断言
3. **对 disabled 元素 `fill()` 静默无效**：保存中输入框 `disabled={busy}`，第二次填值被吞 → 先 `toBeEnabled`
4. **端点变更后断言过期**：`network:allLegionReadsScoped` 写死 `/api/hub/status`，改用 `session-status` 后假红 → 断言接受两个合法端点，**保留「必须带 network_id」语义**
5. **时间窗断言在负载下误红**：见上表

> 共同点：这五类都不会让页面出错，只会让**验收结论错误**。

## 五、三次「改了但没效果」（密度那一版）

1. 只改 CSS `padding` → 节点行高 53 **不变**（被 32px 头像顶住）
2. 加头像缩放（26px）→ 行高仍 53（节点列表是**虚拟化列表**，行高写死 53px）
3. 把行高贯通到虚拟化（`nodeRowHeight` 44/53/62 + `nodeListWindow(..., rowHeight)` + 选中滚动/底部钳制）→ 才生效

教训：**列表行高不是样式，是「布局 + 虚拟化数学」的契约**，只改其中一侧等于没改。

## 六、一次失败的优化（ETag 条件请求），已整套撤回

设想：首页 5 秒轮询 247 KB，内容多半没变 → 304 可省 178 MB/小时。

实测否定：
- 服务端 ETag 成立（curl：200/245,620 B ↔ 304/0 B）
- 但真实页面 60 秒窗口 **0/11 命中**：`progress`/`updated_at`/`last_seen_at` 每轮都变，JSON 哈希必然不同
- 途中两个坑：`If-None-Match` 是 fetch **禁止请求头**（写了会被丢弃）；默认 cache 模式下浏览器可能直接回放本地 200（需 `cache: 'no-store'`）

决定：**不留在代码里**。一个「技术上支持 304、实际零收益」的改动比没有更糟。
